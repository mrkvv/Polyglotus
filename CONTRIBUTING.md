# ВЕТКИ

Стратегия ветвления проекта - **GitHub Flow**: главная ветка `main`, изменения в которую попадают только через PR из короткоживущих веток. Такие ветки начинаются со следующих префиксов:
- `feature/` - для добавления нового функционала
- `fix/` - исправление бага
- `docs/` - ведение документации / репозитория / архитектурные коммиты
- `chore/` - для каких-либо рутинных действий, которые не подпадают под другие категории

Ветка создается ровно на 1 тикет, а после его закрытия - удаляется.

# ТИКЕТЫ
Ответственной за тикеты является [Анастасия](https://github.com/Nao2705), но при необходимости создавать тикеты может любой.

Важно при создании тикета:
- Сразу назначать ответственного. Сделать это можно в разделе `Assignees` справа сверху.
- Сразу выставлять теги. Это в разделе `Labels`.
- Сразу выставлять приоритет и сложность задачи на нашей доске. Сделать это можно в разделе `Projects`. (сначала выберите там нашу `Dashboard`, **потом создайте ишьюс**, и только потом вы сможете раскрыть вкладку с `Dashboard`ом и выставить эти параметры)

Если вы берете тикет или наоборот откладываете в дальний ящик, то необходимо сменить статус тикета (раздел `Projects` -> `Status`).


## ТЕГИ

Делятся на 2 категории:
1) в начале стоит `T` (означает `Task`) => ставятся только на тикеты
2) в начале стоит `PR` (означает `Pull Request`) => ставятся только на пулл реквесты

Список всех доступных тегов и их описание:
- `PR: bug` - Исправлен баг
- `PR: feature` - Добавление нового функционала
- `T: architecture` - Задача, связанная с проектированием
- `T: backend` - Задача, связанная с серверной частью
- `T: chore` - Рутинная задача
- `T: CI/CD` - Задача интеграции/развертывания проекта
- `T: design` - Задача творческого характера
- `T: documentation` - Задача бумажного характера
- `T: frontend` - Задача, связанная с web-разработкой

# КОММИТЫ
Единый формат коммитов - [**Conventional Commits**](https://habr.com/ru/articles/867012/)

Если в кратце, то шаблон сообщения коммита такой:
```
type(scope): сообщение

подробное описание, если нужно
```

ВАЖНО!: Сообщение коммита должно полностью описывать изменения, которые вы вносите. Не должно быть такого, что в коммите у вас указана работа над одним, а изменения присутствуют и в каких-то других файлах.

ВАЖНО!2: Этот же формат соблюдается и при вливании `PR`'ов в `main`-ветку.

---
*Пример: я делаю коммит в микросервис NewsHandlerService*
```
git commit -m "feat(NewsHandler): алгоритм тегирования" -m "Дополнительно:" -m "- вынес некоторый функционал в утилитарный класс" -m "- исправил неработающий acknowledgment в KafkaConsumer"
```

*Результат:*
```
feat(NewsHandler): алгоритм тегирования
Дополнительно:
- вынес некоторый функционал в утилитарный класс
- исправил неработающий acknowledgment в KafkaConsumer
```


# ПУЛЛ РЕКВЕСТЫ

Название `PR`'а так же оформляется по [**Conventional Commits**](https://habr.com/ru/articles/867012/) (только без описания).

После создания `PR`'а следует линкануть его с тикетом, который вы выполнили. Сделать это можно в разделе `Development`. Когда `PR` вольется в main, связанный тикет автоматически закроется.

## ПРИНЯТИЕ ПУЛЛ РЕКВЕСТА

1) Выполнить ревью изменений (вкладка `Files Changed`)
2) Проследить, чтобы изменения не задействовали те части проекта, что не относятся к задаче
3) Если вас все устраивает - `Files Changed` -> `Submit Review` -> `Approve`. В противном случае оставьте автору комментарий и ждите его правок или оправданий
4) Для вливания в `main` необходимо нажать на `Squash and merge`
5) Откроются 2 окна: `Commit message` и `Extended description`. Сейчас вы заполняете сообщение суммарного коммита - все коммиты, сделанные в рабочей ветке "схлопнутся" в тот, что вы сейчас напишите.
6) Согласно [**Conventional Commits**](https://habr.com/ru/articles/867012/) заполнить оба окна. При этом важно отразить абсолютно все изменения, сделанные в вливаемом `PR`'е. Даже если вы не знакомы с предметной областью, постарайтесь собрать итоговое сообщение из коммитов автора.


# Шпаргалка по командам git (префикс ветки может отличаться)

Создание ветки:
```
git switch main
git pull
git checkout -b feature/...
git push origin feature/...
```

Если вы не сделаете `git pull` в `main`'е, то ветка, которую вы создадите будет ответвляться от старой версии `main`'а и во вкладке `Files Changed` это будет очень странно смотреться, к чему 100% будет придираться reviewer.

Далее, после бурной работы с add и commit:
```
git push -u origin feature/...
```

На этом этапе ваши изменения внесены, но `main` мог уже ускакать по коммитам вперед. Вам нужно синхронизироваться и перебазировать все ваши коммиты поверх коммитов из main'а:
```
git checkout feature/...
git fetch origin main
git rebase origin/main
(если будут конфликты, решаете их)
git add .
git rebase --continue
git push --force-with-lease
```

Удаление ветки после успешного мерджа в `main`:
```
// Удалить ветку в репозитории (так же можно выполнить и через UI на github)
git push origin --delete feature/...

// Удалить ветку локально
git branch -D feature/...
```
